Milestones 4 & 5 — workflow, replay, persistence

Concrete UI suggestions for the next two milestones. Each section: a working mock, the rationale, and bullet notes on the data wiring. Mocks are static — they show the shape, not the behavior.

M4 Workflow & Testing
Send · edit · replay against Orchestra (or any MLLP target) without leaving the inspector.
1
Replay drawer — one-click resend with knobs
addresses: replay task
A right-side drawer that opens from a "Replay…" button in the detail header. The source message is locked at top (you can't accidentally replay the wrong one). Target picker is a dropdown of saved connections, not a free-form input — typing host:port every time is friction. Live ACK/latency feedback shown inline after send.

2
Template generator — pick a trigger, edit fields, fire
addresses: test message generator
Templates organized by category in a sidebar. The form is a structured field editor (not free-form HL7) so users don't have to remember segment delimiters. Fields with a ∼ tag are auto-generated on send (timestamp, control ID, UUIDs) — important for sending many messages without collisions. Switch to "Raw" tab for power users.

4
Smart notifications — not "new message" spam
addresses: auto-refresh trigger / desktop notification
A desktop notification on every message is noise. Make it triggerable: notify only when a watched filter matches. "Notify me on parse errors", "notify me when I get a message tagged followup", "notify me when this MRN appears". Configurable from the same chip-style filter UI.

  • Notification rules live next to the filter chips: + Notify on this filter appears when a search has matches.
  • Silence rule by default — "no messages in N minutes" catches the common "is the integration broken?" question.
  • Click on a notification deep-links to the matching message in the Harux UI.
  • Browser Notification.requestPermission() on first rule creation; falls back to in-app toast.
M5 Persistence
Survive restarts, prune sensibly, export anything.
5
Storage settings — single page, visual retention
addresses: SQLite backend + retention policy
Persistence defaults to off (current behavior). One settings page exposes the toggle, the location, and the retention policy. The retention bar shows live what's about to be pruned — way clearer than just a number. Live stats card at the top: how big is my db, how many messages, how full is the retention window.

Manual actions
  • Retention bar is the killer feature — when you adjust the slider, you see immediately which messages would be deleted. Less anxiety than blind numbers.
  • Bookmarks-survive-retention is a small but high-value detail: lets users pin "interesting" messages without setting up complex queries.
  • SQLCipher is a single-line addition over plain SQLite and unlocks healthcare deployments.
  • Storage backend is pluggable — Postgres option matters for multi-instance Harux deployments.
  • Stats cards link to the existing top-bar health pills design language.
6
Export — formats with purpose, scoped to current filter
addresses: extended export
Each format is for a different audience. Cards explain when to use each, instead of a bare dropdown. The export scope always reflects the current filter — clear summary at the bottom: "you're exporting 42 messages matching has:errors from epic.hospital.local".

  • "Anonymize PHI" toggle: replaces patient names / MRNs / addresses with consistent fakes (Faker.js) before writing. Huge for sharing test fixtures.
  • Harux session bundle (.har-ish) round-trips: import a colleague's bundle and see exactly what they saw, with their tags and bookmarks intact. Killer feature for support/debugging.
  • Per-message zip turns Harux into a fixture-generator for your test suite — no more hand-curating `.hl7` files in tests/messages/.
  • Format cards make this self-documenting; new users discover capabilities without docs.
  • Footer summary always reflects the current filter — no surprise giant exports.
7
Post-restart context — show what survived
addresses: persistence acceptance criteria
When persistence is on and the server restarts, messages reappear — but the user might not realize they're looking at "old" data vs "live". Show a small contextual banner above the inbox the first time it loads: "Restored 14,283 messages from disk · last activity 3m ago". Self-dismisses after 10s or on first new message.

Implementation order suggestion 1. Saved targets in harux.toml (M4 prereq) → 2. Replay drawer → 3. SQLite backend + retention (M5 core) → 4. Export modal → 5. Template generator → 6. Raw editor → 7. Smart notifications.

Replay + persistence are the two highest-leverage items: replay turns Harux into a Postman for HL7, persistence turns it into a debugging journal you can come back to.
